## ADDED Requirements

### Requirement: 撈過的資料保留下來不再重打外部服務

使用者 MUST 在系統撈過某月份某 repo 的資料之後，再次查詢就不需要重打外部服務，能立即得到結果。

#### Scenario: 二次查詢瞬間回應

- **WHEN** 使用者第二次查詢同月份同 repo 的指標
- **THEN** 系統不打外部 API，直接回應

### Requirement: 跨月份的趨勢查詢

使用者 MUST 能跨多個月份查同一個 repo 或成員的指標，看到長期趨勢（例如 6 個月失敗率變化）。

#### Scenario: 6 個月趨勢

- **WHEN** 使用者查某 repo 從 2026-01 到 2026-06 的失敗率
- **THEN** 系統回傳 6 筆月份資料，每筆含當月失敗率

### Requirement: 已過月份視為穩定資料

使用者 MUST 不會因為再次跑工具，導致已過月份的資料被改寫，因為過去的事實不應因重撈而改變。

#### Scenario: 過去月份不變動

- **WHEN** 使用者今天 (2026-05) 重新跑 2026-04 的資料
- **THEN** 系統採用既有的 2026-04 資料，不重新撈外部服務

#### Scenario: 當月可更新

- **WHEN** 使用者今天 (2026-05) 跑 2026-05 的資料
- **THEN** 系統允許更新，因為這個月還沒結束、還在累積

### Requirement: 系統升級不應該毀掉歷史資料

使用者 MUST 在系統未來新增分析欄位（例如新增「commit message」之類）時，不需要再去外部重撈過去資料來補欄位，因為過去的回應已被保留可重新解析。

#### Scenario: 補新欄位不重打 API

- **WHEN** 系統未來新增一個源自外部回應的欄位
- **THEN** 系統能從本地保存的原始回應中解析、補回歷史紀錄，不需重打外部服務
